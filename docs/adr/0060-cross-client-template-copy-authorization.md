# ADR-0060: Cross-Client Template Copy -- A Narrow RLS Escape Hatch, Dual-Account Authorization, and Never Copying the Source's Brand Snapshot

**Status:** Proposed
**Date:** 2026-10-21
**Epic:** E9 -- Agency Multi-Client Operations
**Governs:** US-41, FR-22

## Context

E2's ADR-0010 scoped `campaign_template` to the account, explicitly deferring "agency cross-client sharing (US-41)" to this epic and naming the floor it must be built on: no user-private tier, the same role set as campaign creation, and -- critically for this decision -- "the E9 architect should treat account-scoping as the floor they are extending, not replacing." Checking the codebase directly (per this epic's own task instructions) found E1's `POST /agency/clients` already accepts `copy_templates_from` but never implements it: `agency.service.ts`'s own comment states "Template copying would happen here in future epics... For E1, we acknowledge the parameter but no campaign templates exist yet," followed by `templatesCopied = 0` hardcoded. This is a confirmed, genuine gap, not a reinterpretation of existing behavior.

Two things make this more than a matter of wiring up an unused parameter:

**First, a database-correctness problem.** `campaign_template`'s existing RLS policy (`account_id = current_setting('app.current_account_id')`) is a `USING`-only policy, which Postgres applies to every command including `INSERT` when no separate `WITH CHECK` is given. A session authenticated under the source client's own account (the ongoing copy action, which Renata performs after switching into the source client's context, consistent with US-39's own selector) or under the agency's home account (the onboarding-time bulk copy) can therefore never successfully insert a row under a *different*, target account's `account_id` -- which is exactly what cross-client copying needs to do. This is not a bug to route around; it is the same tenant boundary every other table in this platform relies on, and crossing it needs the same explicit, narrow, validated escape-hatch discipline E7 already established for its own cross-client read (`app.agency_cross_client_read`), not an ad hoc bypass.

**Second, an authorization-completeness problem specific to `agency_operator`.** `agency_admin` has implicit access to every client account in their workspace (E1), so for that role, "the operator can reach the source and target" reduces to "both accounts are in the same workspace," already checked. `agency_operator`'s access is per-client (`operator_client_access`), and `RolesGuard`/`AccountAccessService.resolveAccess` only ever resolves access to the **one** account named by the current request's `X-Account-Id` -- the source, in the ongoing-copy case. Nothing in the existing request pipeline checks whether that same operator also has a grant for the **target** account named in the request body, which is a second account the existing single-account-per-request authorization model was never designed to see. Left unchecked, an operator with access to Client A only could name Client B as a copy target and succeed, which is precisely the leak the task's own framing warns against: "don't leak one client's template to another client who isn't the agency's."

Three design questions were resolved together, since they interact:

1. **How does the write cross the RLS boundary?** Options: (a) a new escape-hatch flag mirroring E7's pattern, narrowly scoped and set only after validation; (b) perform the copy as two separate HTTP requests, with the frontend fetching template fields under the source context and re-posting them under the target context, avoiding any single request crossing the boundary at the database layer at all; (c) disable `FORCE ROW LEVEL SECURITY` for this one write, running it as a privileged database role. (b) was rejected because the onboarding-time bulk case (`copy_templates_from` on `POST /agency/clients`) cannot be decomposed this way at all -- the target account does not exist yet until the very request that names it as a copy source for a not-yet-created account, so there is no "switch to the target's context first" step available to the frontend. (c) was rejected because it reintroduces exactly the class of unscoped, privileged-role risk the architecture document's own risk register (R-02) already treats RLS-bypass roles as requiring the strongest justification, for a feature where a narrower, already-reviewed pattern suffices. (a) was chosen.
2. **Who must be checked against the target account, and how?** Resolved as: `agency_admin` needs only the workspace match (implicit access); `agency_operator` needs an explicit, independent `AccountAccessService.resolveAccess` call against the target account, since that account was never the one `RolesGuard` resolved for this request.
3. **Does the copied template carry the source client's brand-profile snapshot?** Resolved as: never. See the architecture document section 2.2 for the full reasoning; summarized in Consequences below.

## Decision

**A fourth escape-hatch flag, `app.agency_template_copy`**, following `app.creator_portal` (E3), `app.aurora_operator` (E6), and `app.agency_cross_client_read` (E7) exactly: a session flag, set only for the duration of the copy write, gating one additional `OR` branch on `campaign_template`'s existing RLS policy, scoped to "any account in the caller's own workspace" -- never platform-wide. `app.current_workspace_id` is reused, not reinvented, as the session variable E7 already introduced for the same purpose.

**The service layer validates before ever setting the flag, in this order:** (1) both source and target accounts belong to the caller's own workspace (404 `CLIENT_NOT_FOUND` otherwise, the same one-code-for-both-cases discipline used everywhere else in this platform for an inaccessible-or-nonexistent resource); (2) if the caller is `agency_operator`, an independent `AccountAccessService.resolveAccess` call against the **target** account must succeed (403 `TARGET_NOT_ACCESSIBLE`, logged, otherwise) -- this is the one genuinely new authorization check this epic adds anywhere, since every other check in this document reuses `RolesGuard`'s existing single-account resolution unchanged. The source side of this same question needs no new check: the request could not have reached the handler at all without the caller already holding resolvable access to the source account, via the exact same mechanism that already protects every other `campaign-templates` endpoint.

**The copied template never carries the source account's `brand_profile_snapshot`.** It is always written as `null`, regardless of what the source template held. A `null` snapshot computes no drift at all (`TemplateService.computeDrift`'s existing short-circuit, E2) -- the conservative, already-existing behavior for "nothing to compare against yet," which is exactly the target client's situation on first receiving a copied template.

## Consequences

**What Aurora gains:**
- Cross-client template reuse ships fully -- both the onboarding-time bulk case (closing E1's year-old dead parameter) and the ongoing, standalone case the stories document's own open question 4 recommends supporting -- using a pattern (a narrow, independently-validated RLS escape hatch) this codebase has already built, reviewed, and shipped three times before. No new category of risk is introduced; this is the fourth instance of an already-understood shape, not a novel mechanism.
- The target-account check closes a real, concretely demonstrable gap in the existing single-account authorization model, rather than assuming `RolesGuard`'s existing machinery already covers a two-account operation it was never designed to see. This is the one piece of this epic's design that could not simply cite "already built by RolesGuard" and required new reasoning, and it is reasoned through explicitly here rather than asserted.
- Never copying `brand_profile_snapshot` across the client boundary closes a subtle cross-client information leak (one client's tone-of-voice and prohibited-topics configuration becoming visible, even indirectly via drift computation, to a template now living under a different client) that the "structure only" framing in US-41's own acceptance criteria already implies but does not spell out field-by-field -- this decision makes that implication explicit and enforced in code, not left to a future engineer's judgment call about what "structure" includes.

**What Aurora gives up:**
- A copied template arrives with no drift-detection history; the target client's team must re-save it as a template from their own campaign once they have run one, to get a real snapshot. This is a one-time, minor loss of convenience in exchange for not fabricating a comparison against a brand profile the target client never configured.
- `agency_template_copy`, like every escape hatch before it, is one more flag the platform's CI allow-list check and any future security review must account for. The cost is identical in kind to the three instances that preceded it, and is the price of supporting a feature (cross-tenant data movement within one workspace) that a purely single-tenant RLS model cannot express at all without some form of explicit, reviewed exception.
- `copied_from_template_id` is a self-referencing FK with `ON DELETE SET NULL` rather than a hard-enforced lineage; if the source template is later deleted, provenance is silently lost rather than blocked. This was judged acceptable since no story requires permanent lineage tracking, only that the copy mechanism itself be safe.
